# CLAUDE.md

Instructions for coding agents working in this repository. Read this first, then the documents it links to.

## State of the repository

Scaffold only. `package.json`, `tsconfig.json`, empty module directories, entry-point stubs and one smoke test per module exist; there is no product behaviour. Everything below marked **planned** is what the plan and the technical specification call for, and it becomes real only when the named ticket merges. Do not report a planned command as working, and do not claim a check passed unless you ran it.

## Product

A TypeScript developer loads an original 2D rigid-body scene, runs it at a fixed 1/60 s tick, pauses at a chosen tick and inspects transforms, contacts, sensor events and constraint errors, in a browser (Canvas 2D) and in a headless Node CLI. The deterministic TypeScript engine covers circles and convex rectangles, friction, persistent contacts, one bounded circle sweep, sensors, distance and revolute joints. A comparison command checks its traces against traces generated by a pinned native Box2D v3.1.1 and names the first mismatching tick, body, field, reference value and observed value.

## Stack and constraints (from the plan)

- TypeScript for the engine, the codec, the CLI and the viewer; Canvas 2D for the viewer; Chrome and a headless Node CLI as targets. Compiler and dependencies are pinned and staged so the work runs offline (PRD "Scope"). Compiled assets are served by a local server; runtime assets and fixtures come from the repository. No external request in the demo.
- The pure engine owns scene validation, stepping and event emission. It has no DOM, no Node API, no wall clock and no random source. The browser renderer has no authority over simulation time.
- Fixed 1/60 s outer tick; four fixed substeps once contacts exist. Bodies iterate by ascending ID, contact pairs by ordered ID tuple, joints by ID, with stable tie breaks. Solver-boundary values are Float32 (`Math.fround` or typed arrays); negative zero is normalised and non-finite state is rejected before a trace is serialised. Tick zero is the initial state; a step creates tick one. Normals point from the lower-ID body to the higher-ID body.
- Scene format version 1: SI units and radians, unsigned integer IDs. Caps: 1 MiB input, 128 bodies, 64 joints, 1,000 ticks, all checked before a world or trace buffer is allocated. Unsupported pairs and invalid input are rejected with specific diagnostic codes.
- The native reference harness is the only component that links Box2D (v3.1.1, commit `8c661469c9507d3ad6fbd2fea3f1aa71669c2fe3`, MIT). Keep its licence and notices. Scenes are original; no external game assets. Expected output is never derived from the TypeScript engine.
- Reference tolerances are proposed until the harness runs: 0.02 m position, 0.05 rad wrapped angle, sensor events matched exactly with at most one outer tick of drift. A divergent fixture is a finding to keep, not something to tune away.
- The project has no licence yet (README "Licensing"). Do not add a `LICENSE` file; it is an owner decision.
- Not pinned by the plan: Node, TypeScript and browser versions. The first ticket records the versions actually used. Do not claim portability beyond them.

## Planned layout

Short version; the dependency rules are in [docs/architecture.md](docs/architecture.md).

- `src/trace/`: scene and replay formats, canonical serialisation. Imports nothing.
- `src/engine/`: validation, stepping, contacts, sensors, sweep, joints, events. Imports `src/trace/` only.
- `src/compare/`: trace comparison and divergence report. Imports `src/trace/` only, never the engine.
- `src/cli/`: headless runner and compare command (Node).
- `src/web/`, `public/`: Canvas 2D viewer and page. `src/server/`: loopback static server (Node standard library).
- `reference/`: native Box2D harness and its notices. `fixtures/`: original scenes, frozen traces, reference traces, tolerances. `test/`: tests.

## Git workflow

- Never work on `main`. One branch per ticket, named `ticket/<issue-number>-<short-slug>`, from the current `origin/main`.
- Small commits with an imperative subject. Open a pull request to `main` that names the issue (`Closes #N`). Only the owner merges and releases. Do not push to `main`, force-push, merge, tag or publish.
- Stay inside the ticket's stated scope. Note anything else you find as a follow-up in the pull request instead of widening the change.
- Documentation-only and planning changes follow the same branch and pull-request rule.

## Evidence before a ticket is called done

Capture, in the pull request description, each command you ran and its observed result:

1. The test command, plus every check the ticket's verification section lists, run locally and passing, with Node version and operating system. For a planned command that does not exist yet, the ticket that introduces it makes it real in the same pull request.
2. Each acceptance criterion mapped to the test, fixture or manual step that proves it. A criterion that needs a person (a keyboard walkthrough in a normal browser) is done as far as an agent can and the rest is listed under "Owner checks"; say which.
3. Determinism and offline checks the ticket touches: canonical trace bytes equal across two runs on the same runtime, no external request from the demo.
4. A statement of what was not run or not verified, including any native (Box2D) step that only CI can run.
5. Review gates, in this order: local checks pass with output recorded; the reviewer inputs are written to `.claude/state/review/`; Code Reviewer reviews the full diff and the recorded output; Reality Checker compares each criterion with the evidence (it does not need a CI result); only then `gh pr create --draft`. CI runs on the draft; fix, re-run the checks and both gates on a red result. Do not poll CI: end the turn with "Draft pull request #N is waiting for CI" and read `gh pr checks` once when woken. Mark it ready only when CI is green, and comment the CI run link on the issue. CI is installed outside the tickets and no ticket edits it.

Never write "done", "passing" or "verified" without the command and its output.

## Delivery workflow

- **Start:** only the owner starts ticket work, with `/next-ticket [issue]` ([`.claude/skills/next-ticket/SKILL.md`](.claude/skills/next-ticket/SKILL.md)). There is no scheduler. Playbook: [`.claude/skills/implement-ticket/SKILL.md`](.claude/skills/implement-ticket/SKILL.md).
- **Review gate hook:** [`.claude/hooks/role-gate.mjs`](.claude/hooks/role-gate.mjs) blocks `gh pr create` and `gh pr ready` until Code Reviewer and Reality Checker ran after the last code edit. `ROLE_GATE=off` in the environment Claude Code is started from switches it off for that session; only the owner does that.
- **Permissions:** [`.claude/settings.json`](.claude/settings.json). Documented commands are allowed; force pushes, pushes to `main`, merges, releases and reads of secrets are denied; edits to CI, agent configuration and Loop files ask first.
- **CI:** [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on Linux and Windows (Node 22) and must be green before a pull request is marked ready. CI runs `npm ci`, `npm run typecheck` and `npm test`. No ticket changes `.github/`. The native reference workflow [`.github/workflows/reference.yml`](.github/workflows/reference.yml) is already installed and skips itself until ticket B2-08 adds `reference/CMakeLists.txt` and `reference/generate.sh`.
- **Pull requests and tickets:** [pull request template](.github/pull_request_template.md), [ticket template](.github/ISSUE_TEMPLATE/implementation-ticket.md). Labels: `status:ready`, `status:blocked`, `status:in-progress`, `needs-decision`, `tracking`. Big tickets are split into sub-issues of 1 to 4 hours; `/next-ticket` picks leaf tickets only and refuses a `tracking` parent; the pull request of the last open sub-issue closes the sub-issue and its parent. Add a line to [CHANGELOG.md](CHANGELOG.md) in every ticket pull request.
- **Only the owner merges and releases** ([docs/RELEASING.md](docs/RELEASING.md)). Security reports: [SECURITY.md](SECURITY.md).
- **UI and writing quality:** [docs/ui-quality.md](docs/ui-quality.md) is binding for every screen; skills `ui-ux-pro-max` (UI work) and `unslop` (copy, docs, pull request text) are installed in `.claude/skills/`.
- **Owner decisions** are recorded in [docs/owner-decisions.md](docs/owner-decisions.md). An agent that finds one blocking a ticket stops and says so.

## Agent roles

Project subagents are in `.claude/agents/`: eight Agency Agents roles (Software Architect, Code Reviewer, Codebase Onboarding Engineer, Application Security Engineer, Accessibility Auditor, Reality Checker, Frontend Developer, Test Automation Engineer) and `loop-verifier`, which belongs to the Loop setup. Each Agency Agents role file starts with a section "In this repository", written for this project: the stack and rules that bind the role, the files it owns or reviews, its commands (planned, as above) or the output it must be given, a checklist, the generic text that does not apply, and what it hands back. That section and this file override the generic text below it. Sources, licence, local changes and the name collision with a user-level install are in [.claude/agency-agents/README.md](.claude/agency-agents/README.md). Reviewer roles are read-only (`tools: Read, Grep, Glob`): give them the diff, the acceptance criteria and the recorded command output.

When asked to implement, continue or finish a GitHub issue, follow the playbook [`.claude/skills/implement-ticket/SKILL.md`](.claude/skills/implement-ticket/SKILL.md). Claude Code loads it on its own for ticket work; `/implement-ticket <issue number>` starts it by hand. Delegate to the roles without waiting to be asked; each role's `description` ends with a "Use proactively ..." sentence, which is what makes Claude Code delegate.

- **Before coding:** Codebase Onboarding Engineer and Software Architect, as their descriptions say.
- **While coding:** the implementing role that matches the files being changed (Frontend Developer for `src/web/` and `public/`, Test Automation Engineer for `test/` and `fixtures/`).
- **After coding:** Application Security Engineer and Accessibility Auditor when their triggers match the change.
- **On every ticket:** Code Reviewer, then Reality Checker, before the draft pull request. The session that wrote a change does not count as its reviewer.
- List the roles that ran and their verdicts in the pull request description under "Agent roles run".
